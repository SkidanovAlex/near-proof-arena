## 4. Hostile package `near-v3-d3-lenient-codes`

There is no runnable expected-rejection test for this package locally. The only automated test is
the pin test, and it passes. A worker e2e run needs a server
(`adversarial/e2e/run_hostile.py --server`). Its materialized tree
(`run_hostile.py --target near-v3 --only near-v3-d3-lenient-codes --materialize`) was built
with `build.sh`. **The build fails**: `ReadCanonDefs.lean:34: unknown identifier encP`, plus
invalid-projection errors.

The cause is not the re-freeze. The overlay `formal/ReexecV3D3/Canon.lean` dates from the first
reference (`935167ee`). The read-set rewrite (`2d9d4e58` and later) moved definitions into
`CanonDefs`/`NormDefs`. `ReadCanonDefs` now uses `encP` and `initPools` from `Canon`, which the
overlay lacks. In addition, the deployed verifier no longer calls `canonW`: `Model` uses
`Read.check`, which requires exact equality with the read-set encoding. So the overlay's attack
(keeping the code list in `canonW`) would not make the deployed verifier malleable even if it
compiled.

As packaged, the case would be rejected at build time, not at ADVERSARIAL_PROOFS with
HOSTILE_PROOF_ACCEPTED as `expect.json` states. Fixing it requires redesigning the attack against
the read-set verifier: for example, a `Read.check` that drops the code-blob part of the equality.
That is a change to the adversarial suite, outside this lane's scope (candidate package only), so
it was left unchanged.
