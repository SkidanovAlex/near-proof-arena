### Design choices made here (inside the user decisions)

* **A7ᴰ¹ keys** = the trie `checkD1` builds: `mainKeys … ++ txKeys w.txs`, i.e. the signer account
  and access key of *every* transaction (duplicates, expired, bad signatures included), not only
  of the candidates. This keeps A7 a function of the relation's own trie and over-approximates
  what an AIR walking only candidate keys hashes. On public-d1 this differs from "read keys only"
  on 2 of 188 cases (the check is live).
* **T1 counts `transactions` as decoded** (duplicates included). `new_transactions` unbounded
  (no T2: P-D1-5 keeps 64 MiB).
* **Order** of `checkD1a`: `checkD1`, then A1, A2, Canon0f, A7, A8, A9, A10, A12, T1 (as `checkD0a`,
  T1 last). An over-bound invalid chunk is therefore a `reject`, not `out_of_domain`.
* `a1`, `a8`, `a12` are reused from `ChunkValidationV0a` (claim only); `walkD0` too.
* Tier: new constructor appended (`| d1a` last, so existing constructor indices are unchanged);
  ranks `D0a 0, D0 1, D1a 2, D1 3, D2 4, D3a 5`.

* Constructed mutants at the real bounds (`public-d1a/mutants`, 2 bases each): T1 4,096 → accept,
  4,097 → `w.tx_count`; A10 32 → accept, 33 → `w.path_depth`; empty main pre-state → reject.
  Lean = Python = expectation on 10/10; oracle `tx_count` (nearcore borsh) = 4,096 / 4,097 and
  `unfold` equal on the 8 measured.
* Cost note: the plain-spec Lean checker needs ≈ 2–3 min per 4,096-transaction mutant (list-based
  SHA-256 / dedup, and the measures re-run the D1 transition); Python ≈ 1 s. A D1a verifier's
  native transaction prep needs fast paths (design §4.1) to stay well inside 60 s at NT0.

### Oracle (`oracle/v3-d1a`)

Offline only (no TestEnv; nearcore `near-primitives` / `near-store`), built with a shared
`oracle/target` (`cargo build --release -j 2`, ≈ 10 min after the `v3-d1` build had compiled the
common crates). `measure-case --dump F`: nearcore borsh decoding of the witness; T1 =
`transactions().len()`; A7ᴰ¹ on `RawTrieNodeWithSize` with the D1 main keys from nearcore
`TrieKey`s (D0 read keys + every transaction's `Account` / `AccessKey`), post blobs as preimages
(cannot steer the count), counting code copied from `oracle/v3-d0a/src/d0a.rs` (private there);
A10 from the `MerklePath`s. `cargo fmt --check` clean; clippy not run.

What nearcore cannot judge here (stated, not hidden):
* the T1 / A10 mutants' `Rel` is by construction (hash chain restored; duplicates are skipped by
  `UniqueChunkTransactions`); judging them with nearcore's validator needs the online
  injection of `oracle/v3-d0a/src/pathmut.rs` in a D1 chain generator — not done (it would need a
  copy of `oracle/v3-d1`'s generator, whose tree is pinned by the draft);
* A9ᴰ¹ (scheduler replica) and A1 / A2 / Canon0f / A8 / A12 are not re-measured on nearcore
  objects for D1 — they are the D0a predicates on unchanged inputs (transactions add no source
  proofs, no `0x0f` writes, nothing to the claim), and the D0a oracle checked them on D0 chains.
* `oracle/v3-d1` (generation) and `oracle/v3`, `oracle/v3-d0a` are unmodified.
